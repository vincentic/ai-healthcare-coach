# 软件工程实践路线

> 目标：从会写功能，升级到能把想法拆成任务、持续交付、部署上线、复盘改进的工程实践能力。每一步都要留下一个可访问、可展示、可复用的作品。

## 实践原则

- 每个练习都要有明确问题：解决谁的什么场景。
- 每个功能都要进入 GitHub：需求、提交、分支、PR 或提交记录可追溯。
- 每个阶段都要部署到 Vercel：让作品从本地代码变成真实链接。
- 每次上线都要写复盘：做了什么、遇到什么问题、下一步怎么改。
- 每周至少完成 1 个可展示版本，而不是只看课程或只写笔记。

## 每一步交付流程

1. 写一句目标：这次要解决什么问题。
2. 拆 3-5 个任务：页面、数据、交互、样式、验证。
3. 建立 GitHub 记录：提交信息写清楚改动意图，并推送到远程仓库。
4. 本地验证：至少检查桌面和手机宽度。
5. 部署 Vercel：保留生产链接或预览链接，并确认线上页面可访问。
6. 写复盘：记录问题、取舍、下一次改进、GitHub 链接和 Vercel 链接。

## 每步更新 GitHub / Vercel

| 节点 | GitHub 要更新 | Vercel 要更新 |
|---|---|---|
| 开始前 | 新建或更新 Issue / 任务清单 | 确认当前线上版本可访问 |
| 完成一个小功能 | 提交并推送代码，提交信息说明意图 | 需要展示时触发预览部署 |
| 本地验证通过 | 更新 README、复盘或验收记录 | 部署到 Vercel 并检查预览链接 |
| 周任务收尾 | 汇总本周提交、Issue 和变更说明 | 把最终部署链接写入 README / 复盘 |
| 下周开始前 | 根据复盘新建下一步任务 | 确认线上版本和计划版本一致 |

## GitHub 提交规范

| 类型 | 使用场景 | 示例 |
|---|---|---|
| feat | 新增功能或页面 | `feat: add engineering practice roadmap` |
| fix | 修复问题 | `fix: correct mobile tab layout` |
| docs | 文档更新 | `docs: add deployment checklist` |
| style | 样式调整 | `style: refine practice card spacing` |
| chore | 配置、目录、杂项 | `chore: update vercel config` |

## Vercel 部署检查

- 首页是否能打开。
- 新增 tab 是否能切换。
- Markdown 是否能预览。
- 外链、原文链接是否正确。
- 手机宽度下文字是否不溢出。
- 部署后的 URL 是否写进复盘或 README。
